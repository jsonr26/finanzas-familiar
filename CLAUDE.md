# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Qué es

App web de finanzas familiares (UI y datos en español, moneda COP). No tiene backend: se empaqueta como **un solo `Finanzas.html`** (vite + `vite-plugin-singlefile`) y guarda todo en un archivo `finanzas.sqlite` dentro de una carpeta de OneDrive elegida por el usuario. Solo funciona en Chrome/Edge de escritorio (File System Access API).

## Comandos

```bash
npm run dev                          # servidor vite
npm run build                        # vite build + copia dist/index.html -> Finanzas.html (este archivo SÍ se versiona)
npm test                             # vitest run (entorno node)
npx vitest run tests/repo.test.js    # un solo archivo
npx vitest run -t "saldo anterior"   # un solo test por nombre
```

No hay linter. Tras cambiar código de `src/`, ejecuta `npm run build` para regenerar `Finanzas.html`.

## Arquitectura

Capas, de abajo hacia arriba:

- **`db.js`**: envuelve sql.js (variante `sql-asm`, sin WASM, para caber en un solo HTML). La base vive en memoria; `all/get/run/transaction` son la única vía de acceso (`run` devuelve el `last_insert_rowid`; `foreign_keys` está activado). `run` y `transaction` lanzan error si `isReadonly()` y notifican a `onChange` (así `storage.js` programa el guardado). Las migraciones corren siempre al abrir (en solo lectura quedan solo en memoria: nada se guarda en ese modo). En los tests, `openDatabase(null)` en un `beforeEach` da una base vacía y ya migrada.
- **`schema.js`**: `MIGRATIONS` es un arreglo; el elemento *i* lleva `PRAGMA user_version` a *i+1*. **Para cambiar el esquema agrega un elemento nuevo, nunca edites uno existente**, y actualiza el `user_version` esperado en `tests/db.test.js`. Los archivos de usuarios reales ya migrados no se pueden reescribir; una versión antigua de la app rechaza archivos con versión mayor.
- **`storage.js` + `lock.js`**: guardado del archivo en la carpeta (handle persistido en IndexedDB), backups en `backups/` (30 conservados), y bloqueo de edición con `finanzas.lock` + latido (TTL 90 s) para que dos equipos no editen a la vez; el segundo queda en solo lectura. `lock.js` es lógica pura y está testeada; `storage.js` depende del navegador y no tiene tests.
- **Contador de bloqueo**: en solo lectura `storage.js` revisa `finanzas.lock` cada 10 s (`iniciarVigilancia` → `reintentar`) y pasa solo a edición cuando se libera; el banner de `main.js` muestra «última señal hace X s» y los segundos que faltan para que caduque (`lock.segundosParaLiberar`/`haceSegundos`). Es una cota: si el otro equipo sigue activo su latido (30 s) renueva el bloqueo y no hay un tiempo real de espera.
- **`repo.js`**: todas las consultas/comandos de dominio (SQL vive aquí, no en las vistas). Las fechas son texto `AAAA-MM-DD`; los rangos de mes usan `inicioMes/inicioMesSig` de `calc.js` (`fecha >= inicio AND fecha < inicioSig`).
- **`calc.js`**: lógica pura sin DOM ni DB (formato COP, `parseMonto` tolerante a `1.234,56`/`1,234.56`, `neto`, fechas locales). Ponla aquí si quieres poder testearla.
- **`ui.js`**: `formulario()` (modal genérico basado en `<dialog>`, devuelve valores o `null`), `confirmar`, `alerta`, `intentar`. En un `select`, `agregar: 'Texto'` añade la opción «➕ …» con un campo de texto para crear un valor nuevo.
- **Inicio** (`views/inicio.js`, vista por defecto): cifras del mes, «Por pagar pronto» (vencidos y de los próximos 7 días, con «Pagar» que usa el mismo flujo que Mes: tarjeta → `pagarMesTarjeta`, autopréstamos → `pagarMes`) y avance del presupuesto por grupo. El resumen de 12 meses sigue en «Resumen anual». **Paleta global** (`paleta.js`, Ctrl/Cmd+K): vistas, «Agregar movimiento» y conceptos (`conceptos.buscarConcepto` abre Conceptos ya filtrado).
- **Tema** (`src/tema.js`): «sistema» (por defecto, sigue `prefers-color-scheme`), «claro» u «oscuro»; se guarda en `localStorage` (`finanzas.tema`) y se aplica como `data-tema` en `<html>` (un script en `index.html` lo pone antes de pintar para evitar el destello). El botón vive al pie del menú lateral y en la paleta Ctrl K. Los colores oscuros están en dos bloques de `styles.css` (media query y `[data-tema="oscuro"]`): si cambias uno, cambia el otro.
- **Campos con buscador**: en `formulario()`, `type: 'buscar'` es un `select` con búsqueda (sin tildes ni mayúsculas, todas las palabras en cualquier orden: `calc.coincide`); acepta `options`, `vacio` y `agregar`, devuelve el `id` (campo oculto con el nombre del campo) y con `required` exige elegir de la lista. Se usa en Concepto de movimiento e ingreso (Mes) y en Grupo (Conceptos). Presupuesto tiene además un filtro por nombre/grupo que solo oculta filas.
- **`main.js` + `views/`**: `main.js` maneja la pantalla de conexión, el marco de la app (menú lateral agrupado en `GRUPOS`, plegable, con insignia de pagos urgentes en Mes; encabezado con título, selector de mes, búsqueda global y «+ Agregar») y el render de la vista activa. Cada vista exporta `{ titulo, icono, periodo?, render(main, { rerender, ir }) }` (`periodo: true` hace que el encabezado muestre el selector de mes de `periodo.js`; las vistas ya no lo pintan ellas; `ir(clave)` cambia de vista) y se registra en `views/index.js`. Las vistas se re-renderizan completas (`rerender()`) tras cada escritura; por eso el estado de UI que deba sobrevivir (p. ej. la vista actual) vive en variables de módulo, y la suscripción a `storage` evita el re-render mientras hay un campo con foco. Las que faltan son placeholders (`pendiente(...)`) con su número de fase.

## Convenciones

- **Solo lectura**: todo control que escribe debe llevar el atributo `data-edit` (el CSS lo desactiva con `body.readonly`) y las escrituras van envueltas en `intentar(...)` para mostrar el error de `run` en vez de romper la vista.
- Los conceptos no se borran si tienen historial (`usosConcepto`): se dan de baja (`activo = 0`). La baja tiene fecha (`fecha_baja`): un concepto inactivo deja de contar **desde el mes de esa fecha** en presupuesto (gastos e ingresos), proyección, Resumen anual y «Por pagar» (`calc.activoEnMes`, aplicada dentro de `montoPrevisto` y `pendientesDePago`), y sus ajustes manuales se ignoran; los meses anteriores conservan su presupuesto y los movimientos nunca se tocan. Un inactivo sin fecha no cuenta en ningún mes. No se puede inactivar desde un mes futuro. `guardarConcepto` solo cambia el estado si recibe `activo` explícito; `darDeBaja(id, desde)` es el atajo (el préstamo pagado se da de baja desde el mes siguiente al último pago). `deudaPendienteConcepto` sirve para avisar antes de dar de baja un concepto de tarjeta/préstamo con cuotas pendientes. `conceptos.notas` (v10) es texto libre; `formulario()` soporta `type: 'textarea'`.
- Los descuentos se guardan con monto **positivo** y `clase = 'descuento'`; `neto()` los resta.
- `conceptos.dia_pago` se deriva de `fecha_pago` al guardar (compatibilidad); la periodicidad (`mensual|anual|manual`) define cómo interpretar la fecha (`describirPago`).
- **Cada N meses**: `conceptos.cada_meses` (1–12, v8) solo aplica con periodicidad `mensual`; el mes de `fecha_pago` es uno de los meses de pago y se cuenta de N en N también hacia atrás (`calc.aplicaEnMes`). En la UI se elige una «Frecuencia» (`calc.FRECUENCIAS`: mensual, 2, 3, 6 meses, anual, puntual) que `desdeFrecuencia`/`frecuenciaDe` traducen a periodicidad + `cada_meses`; con N > 1 la fecha de pago es obligatoria (`guardarConcepto` lo valida). `monto_estimado` es lo que se paga *cada vez*. Presupuesto, proyección, Por pagar y Resumen anual lo respetan porque pasan por `aplicaEnMes`; la CHECK de `periodicidad` (v3) no se pudo ampliar, por eso es una columna aparte.
- **Quincenal** (v11): `conceptos.quincenal = 1` (con periodicidad `mensual` y `cada_meses = 1`; no se combina con «cada N meses») = dos pagos fijos al mes, el 15 y el último día (`desdeFrecuencia('quincenal')`). `monto_estimado` es lo de cada pago y el previsto del mes es el doble (`montoPrevisto`; un ajuste manual es el total del mes; vale también para ingresos). `fecha_pago` no se usa. `calc.pendientesDePago` genera un pendiente por cada pago que falta (2 − `n_mov`, siempre los últimos) con `pago` (1|2) y `monto_pago` (mitad del previsto); la vista Mes identifica cada fila con `id-pago`.
- Nombres de código, tablas y textos de UI en español; los comentarios también.
- El plan está organizado por fases (ya tienen vista Conceptos, Mes, Presupuesto, Tarjetas, Cuentas, Cajas de ahorro, Autopréstamos y Resumen anual; el plan por fases está completo).
- **Vista Mes** (`views/mes.js`): resumen compacto (saldo del mes + ingresos, gastado, ahorro, % de presupuesto; «Ver detalle» muestra saldo anterior, descuentos, presupuesto y gasto por grupo), **barra de registro rápido** (`#rapido`: movimientos o ingresos según la pestaña; usa `ui.camposHTML` + `ui.enlazarFormulario`, los mismos campos y comportamiento que el cuadro modal; Enter guarda, conserva fecha/cuenta/persona y deja el cursor en «Concepto»; «+ Más campos» agrega pagó/nota; el atajo N enfoca la barra), franja de **último registro** (`repo.ultimoRegistro`: el de mayor `creado_en` entre movimientos e ingresos de cualquier mes, con Editar/Deshacer o «Ir a ese mes»), y tres pestañas (Movimientos agrupados por día con subtotal y fichas de filtro, Ingresos por quincena, Por pagar). «Registrar» en Por pagar pasa concepto y monto a la barra (`pendienteRapido`); las tarjetas siguen con `pagarMesTarjeta`; los conceptos de tarjeta siguen bloqueados en la barra. La v16 añade `movimientos.creado_en` e `ingresos.creado_en` (ISO UTC, se pone al insertar y no cambia al editar; los registros anteriores quedan sin hora). `editarMovimiento`/`editarIngreso` (cuadro modal) se usan para editar y desde el encabezado.
- **Presupuesto**: el monto base de un gasto es `conceptos.monto_estimado`; la tabla `presupuesto` guarda solo *ajustes de un mes* que mandan sobre el base (un ajuste de 0 cuenta). El base aplica a todos los meses (también los pasados) según `periodicidad`/`fecha_pago` (`aplicaEnMes`). Toda esa lógica vive en `repo.gastosMes` + `calc.montoPrevisto`.
- **Saldo anterior**: es automático (`calc.saldoInicial` encadena ingresos netos − movimientos de todos los meses previos, **partiendo de la suma de los saldos iniciales de las cuentas** — `repo.saldoBaseCuentas`, las mismas que suma Cuentas —, así el saldo de Mes/Inicio/Resumen/proyección cuadra con el total de Cuentas; un saldo manual ignora esa base y reinicia la cadena); `saldos_mes` solo guarda sobrescrituras manuales, que además reinician la cadena hacia adelante.
- **Por pagar**: `calc.pendientesDePago` se calcula (sin tabla) con conceptos que tienen `fecha_pago`, ningún movimiento en el mes y **previsto mayor que 0** (sin monto estimado, con ajuste de 0 o cubiertos del todo con tarjeta no salen, ni en Mes ni en Inicio ni en la insignia del menú; se pueden registrar igual con «+ Agregar»); no se calcula para meses pasados.
- El mes/año consultado vive en `src/periodo.js` y lo comparten las vistas Mes y Presupuesto.
- **Proyección** (vista Presupuesto): `repo.proyeccion` encadena `calc.proyectarMeses`; gastos/ahorro = presupuestado del mes (en el mes inicial, el mayor entre presupuestado y ejecutado) e ingresos = los presupuestados (conceptos `ingreso`/`descuento` con `monto_estimado`, vía `repo.ingresosPresupuestoMes`; lo ejecutado sale de la tabla `ingresos`) o, si no hay ninguno, los registrados o el neto del último mes con ingresos (`origen`).
- **Cuentas bancarias**: `ingresos.cuenta_id` y `movimientos.cuenta_id` (nullable). `repo.saldosCuentas` = saldo inicial + ingresos netos − movimientos acumulados hasta el cierre del mes; lo que no tiene cuenta va en `sinCuenta` para que el total cuadre. `cuentas_saldos` guarda el saldo real del banco anotado por mes (conciliación).
- **Tarjetas de crédito**: la compra no es gasto hasta que se paga. `compras_tarjeta` genera `cuotas_tarjeta` (`calc.calendarioCuotas`, sistema francés); `repo.pagarCuotas` crea UN movimiento por la suma en el concepto «Tarjeta X» y marca las cuotas con `movimiento_id` (FK `ON DELETE SET NULL`: borrar ese movimiento reabre las cuotas). Desde «Por pagar» de Mes, el pago de una fila de tarjeta (`repo.tarjetaDeConcepto`) abre `tarjetas.pagarMesTarjeta` (cuotas del mes + vencidas preseleccionadas → `pagarCuotas`), no el formulario genérico; y la vista Mes **bloquea** crear un movimiento nuevo (o cambiar uno a ese concepto) en un concepto de tarjeta, porque no bajaría la deuda. Los movimientos ya existentes se siguen editando. Las cuotas que vencen en un mes son el `previsto` del concepto de la tarjeta (`cuotas_mes` en `gastosMes`). `repo.actualizarCompra` edita una compra y recalcula: sin cuotas pagadas rehace el calendario; con pagos NO toca lo pagado y recalcula solo las pendientes (capital que falta = monto − capital pagado, repartido en cuotas − pagadas, desde la primera pendiente, saltando meses ocupados por cuotas pagadas fuera de orden). Las pendientes se actualizan en su sitio (conservan id) y los números se reordenan por fecha. `actualizarTarjeta` renombra también el concepto «Tarjeta X». La vista Tarjetas muestra cada tarjeta dibujada (`dibujo` en `tarjetas.js`: nombre, últimos 4 dígitos, deuda, por pagar del mes, día de pago, cuenta, barra de cupo y etiqueta «Vence en N días» solo en el mes en curso); al hacer clic se abre su detalle (`abierta`, variable de módulo; «← Todas las tarjetas» vuelve; siempre se muestra la lista primero, aunque haya una sola). La v14 añade `tarjetas.ultimos4` (solo 4 dígitos, validado), `cupo` y `color` (`repo.COLORES_TARJETA`; sin color se reparte por id), todos opcionales; `repo.tarjetas()` trae además `fecha_pago` (del concepto) y `cuenta`. **Compra que cubre uno o varios conceptos** (v13, tabla `compras_cubre`: compra, concepto y el monto de la compra que le corresponde; `compras_tarjeta.concepto_id` de la v12 quedó sin uso): cada cuota cubre a cada concepto en proporción `monto_concepto / monto_compra` (intereses incluidos). `repo.guardarCompra/actualizarCompra` reciben `cubre: [{concepto_id, monto}]` (en `actualizarCompra`, ausente = no cambia, presente = reemplaza; la suma no puede pasar del valor de la compra y bajar el valor por debajo de lo asignado se rechaza). En el formulario se usa el control `lista-monto` de `formulario()`. en los meses en que vencen sus cuotas, la parte de esas cuotas que le toca se resta del previsto del concepto (`cubierto_tarjeta` en `gastosMes`, `montoPrevisto`) y, si lo cubre del todo, deja de salir en «Por pagar» (`pendientesDePago`; `cubiertosConTarjeta` alimenta la línea informativa de Mes). El dinero cuenta una sola vez, dentro de «Tarjeta X»; el «ejecutado» del concepto no cambia. Solo conceptos de gasto activos, no quincenales ni de tarjeta/préstamo (`repo.conceptosCubribles`); el vínculo se conserva al editar aunque el concepto se inactive.
- `db.transaction` se puede anidar (la interna participa de la externa y las notificaciones salen al final de la externa).
- **Resumen anual** (vista inicial): `repo.resumenAnual(anio)` agrega los 12 meses (ingresos netos, gastos, ahorro, presupuesto, saldo de cierre) llamando a `gastosMes` por mes; el gráfico es SVG inline con variables CSS del tema. Comparte el año con las demás vistas vía `periodo.js`.
- **Cajas de ahorro dibujadas**: igual que Tarjetas, la vista muestra cada caja como tarjeta (`dibujo` en `cajas.js`: ícono según el nombre con `calc.iconoCaja` —💰 fija para la caja de ganancias—, saldo, tasa EA, rendimiento del mes, banco, «Prestado a la familia · N % recuperado / por recuperar» tomado de `repo.prestamosPorCaja`, y barra de meta) y al hacer clic abre el detalle (`abierta`; siempre lista primero). La v15 añade `cajas_ahorro.color` (mismos colores que las tarjetas, `src/colores.js`) y `meta`, opcionales; `repo.guardarCaja` conserva color/meta si no vienen en los datos y solo los borra con vacío explícito.
- **Cajas de ahorro** son informativas: sus aportes/retiros (`cajas_movs`) NO crean movimientos ni tocan Cuentas, Presupuesto ni Resumen. El rendimiento es una estimación (`calc.estimarRendimiento`, interés compuesto diario con la EA vigente cada día de `cajas_tasas`; `tasa_ea` es una fracción) comparada con lo registrado como `rendimiento`. No se guarda ninguna tasa fija en el código: el usuario anota la del banco.
- **Autopréstamos dibujados**: la vista `prestamos.js` muestra cada préstamo como tarjeta (`dibujo`: de qué cajas sale, falta por devolver, cuota, próxima fecha, interés mensual, barra y «N de M cuotas pagadas», etiquetas «N vencidas»/«Pagado ✓»; los pagados van aparte bajo «Pagados»; color automático por id, sin campo en la base) y al hacer clic abre su detalle (`detalleId`; siempre lista primero). La proyección por mes y «Qué ha prestado cada caja» quedan en la lista, debajo de las tarjetas.
- **Autopréstamos** (vista `prestamos.js`): se financian con una o varias cajas (`autoprestamos_origen`). Crear uno registra un `retiro` en cada caja (`cajas_movs.autoprestamo_id`) y genera `cuotas` (cuota fija, `calc.calendarioCuotas`; `tasa_mensual` es fracción). Como las tarjetas, pagar cuotas crea UN movimiento en el concepto «Autopréstamo X» (sus cuotas del mes son el `previsto`, vía `cuotas_mes`) y además, por cada cuota, un `aporte` de CAPITAL a cada caja de origen (repartido con `calc.repartir`) y un `aporte` del INTERÉS a la caja de ganancias (`repo.cajaGanancias()`, creada sola y guardada en `config.caja_ganancias`); todos llevan `cajas_movs.cuota_id`. Los pagos anteriores a este cambio devolvieron capital+interés a las cajas de origen y no se migraron. Cuota pendiente = `cuotas.movimiento_id IS NULL` (las columnas `pagada`/`fecha_pago` de la v1 no se usan). `repo.eliminarMovimiento` es el único camino que debe usarse para deshacer un pago: quita también esos aportes y reabre el préstamo. Al pagarse todo el préstamo, su concepto se da de baja. `repo.prestamosPorCaja` da el control por caja (prestado, devuelto, falta, intereses, fecha de término). **Proyección y pago del mes**: `calc.proyectarPagosPrestamos` agrupa por mes las cuotas de los préstamos activos (`repo.cuotasDePrestamosActivos` / `proyeccionPagosPrestamos`; saldo posterior, vencidas, estado) y `calc.seleccionarCuotasMes` elige las del mes (+ vencidas anteriores). `prestamos.js` exporta `pagarMes(anio, mes, rerender)` (diálogo con todo preseleccionado, casilla de incluir vencidas y cuenta editable por préstamo) que llama a `repo.pagarCuotasPrestamos`: UN movimiento por préstamo, todo o nada. Se usa desde la fila de la proyección, el aviso «Pagar ahora» y la línea «Autopréstamos» del panel Por pagar de Mes. No hay registro automático: la app no tiene servidor, siempre se confirma.
- **Calculadora** (`calc.evaluarExpresion`/`esExpresion`/`formatoDinero`, sin `eval`; `src/calculadora.js`): los campos `money` aceptan operaciones (`1.200.000 + 350.000 * 2`; punto = miles, coma = decimal, `n%` = n/100, resultado a 2 decimales): se ven en vivo, y Enter, «=» o salir del campo las convierten en su resultado; `leer()` y el envío ya devuelven el resultado, así que las vistas siguen recibiendo un número en texto. Un botón 🧮 (solo visible al editar el campo) abre la calculadora con «Usar resultado»; la calculadora suelta está en el pie del menú lateral y en Ctrl K (copia al portapapeles, historial en `localStorage` `finanzas.calc`).
- **Campos de dinero**: en `formulario()`, `type: 'money'` da formato de miles al escribir (`calc.formatearEntrada`: punto = miles, coma = decimal) y `parseMonto` lo lee de vuelta; para tasas/porcentajes usa `type: 'decimal'` (sin formato). `vistaPrevia(valores)` pinta HTML en vivo bajo los campos (se usa para recalcular cuotas al cambiar la tasa).
- **Tasa de referencia**: `src/referencias.js` guarda la EA de la tarjeta de crédito de Nu (28,59 %, tarifas de octubre de 2026) como valor por defecto del interés de un autopréstamo; es solo un punto de partida y hay que actualizarla a mano. `repo.cambiarTasaAutoprestamo` recalcula solo las cuotas pendientes.
- **Reinicio**: `repo.borrarTodo()` vacía todas las tablas (lista explícita, en orden de claves foráneas: al agregar una tabla nueva hay que añadirla ahí; el test de `borrarTodo` la cubre) y vuelve a sembrar los grupos base. El botón vive en Conceptos («Zona de peligro»), exige escribir BORRAR y antes llama a `storage.respaldarAhora`, que guarda `backups/finanzas-antes-de-borrar-<fecha>.sqlite` (fuera de la rotación de 30). Si el respaldo falla, no se borra nada.
- **Conceptos que abonan a una caja** (v9): `conceptos.caja_id` fuerza `categoria = 'Ahorro'` al guardar. `repo.guardarMovimiento` mantiene un aporte ligado en `cajas_movs.movimiento_id` (`sincronizarCajaDelMovimiento`): se crea, se actualiza o cambia de caja al editar, se borra si el concepto ya no tiene caja, y un monto negativo es un `retiro`; `eliminarMovimiento` lo borra. Cambiar la caja de un concepto no reescribe pagos anteriores. Esos aportes no se editan desde Cajas (se ven como «desde un pago»). Las tarjetas y los autopréstamos no se ven afectados (sus conceptos no tienen caja).
